Abstract
========

This PEP proposes to add a means for users to safely and efficiently
share arbitrary objects (or at least a copy of their data) between
multiple interpreters in the same process.  This would be an
improvement over the basic and inefficient data sharing that
currently exists.  The proposed solution involves three parts:
add C-API, add a new ``PyTypeObject`` slot, and add a new
Python object special method.


Motivation
==========

The main deficiency for people using multiple interpreters is with
efficiency.  The main area of inefficiency is communication between
interpreters and otherwise sharing data between them.  Improving
efficiency there would have a meaningful impact on the usability
of multiple interpreters.


"Sharing" Objects
=================

"Sharing" between interpreters refers to sending data *represented* by
objects.  It does not mean multiple interpreters are using the same
object at the same time (with a very small number of exceptional cases).

By default, most objects are copied with :mod:`pickle` when they are
passed to another interpreter.  Nearly all of the immutable builtin
objects are either directly shared or copied efficiently.  For example:
Actually sharing objects (or other data) between interpreters is tricky.
Any data actually shared between interpreters loses the consistency
and thread-safety provided by the isolation of each interpreter,
particularly the :term:`GIL`.

Thus, sharing *mutable* data requires some coordination or frequent
synchronization and context switching.  That can quickly make it
expensive.  Any data tied to one interpreter's lifetime, even immutable
data, faces similar complexity.

Python objects, with very few exceptions, are always mutable and always
tied to the interpreter where they were created.  Therefore they can't
be truly shared without significant extra cost.

Consequently, sharing objects and other data between interpreters must
be done thoughtfully and carefully, even if only for short communication
exchanges.  There are several effective approaches to doing so.

Pure Python code doesn't have the capacity to accomplish any of these,
at least not fully.  Instead, the :mod:`!concurrent.interpreters` module
and the runtime provide help.

The simplest approach is to make a copy of the original data for use
in a target interpreter.  This often involves some form of
serialization.  This *can* be done efficiently, especially by the Python
runtime and within extension modules, but not always.  Most notably,
copying means mutable objects won't stay in sync.

When the shared data is especially large, it often makes sense to
actually share it, such as through the
:ref:`buffer protocol <python-buffer-protocol>`.  Then the interpreters
must cooperate on reading and writing, whether through locks or
assigning partitions or something else.

Regardless of the approach, nearly all "sharing" between interpreters
involves brief communication exchanges.  The data is almost always
shared only for the duration of the exchange.

In general, the exchange between interpreters looks like the following:

1. convert an object to raw, cross-interpreter safe data
2. pass the data to another interpreter
3. convert the data back into an object

The runtime provides support for those steps.  Pure Python code has
access to that support through the :mod:`!concurrent.interpreters`
module.  For example, both :meth:`Interpreter.prepare_main` and
:class:`Queue.put() <Queue>` implement the exchange.
:func:`as_shareable` can help with the two conversion steps.


Specification: Python Code
==========================

Conversion Functions
--------------------

The runtime support for the two conversion steps (convert to raw data
and back) is low-level and not directly available to pure Python code.
However, we will add a standardized protocol that fills the gap:

Most objects do not have that low-level support, including instances
of all pure Python classes.  Such objects cannot be shared without some
other mechanism to manage the conversion, like the default fallback
of :meth:`Interpreter.prepare_main` (pickling).  Aside from such
fallbacks, the standardized way for code to bridge that gap will be
with a "conversion function".

A conversion function takes an object and returns an object that
supports low-level conversion.  It also returns a "restore" function
that turns the converted object back into an equivalent of the original.
(In some uncommon cases, the restore function may be ``None``, meaning
the converted object should be used as-is.)

The restore function will be converted to cross-interpreter data and
back during the exchange, so the function must be stateless.  This
means it cannot rely on external state nor on internal state.  It may
rely on arguments and builtins but not on globals or a closure.
A stateless function is equivalent to its code object.

Special Method
--------------

The the sharing-related functions and methods in
:mod:`!concurrent.interpreters` all support one conversion function in
particular: the :meth:`~object.__xidata__` special method.  Thus classes
that do not provide a low-level implementation for sharing may still
control how they are shared by implementing ``__xidata__()``,
which acts as a conversion function.

* ``object.__xidata__() -> (converted, restore)``
      Converts the object to one that is sharing-compatible.  Returns
      ``(converted, restore)``, where "converted" is the object to "share".

      For classes that directly support conversion to cross-interpreter
      data, ``__xidata__()`` returns ``(self, None)``.

concurrent.interpreters functions
---------------------------------

We will add the following functions to the
:mod:`concurrent.interpreters` module:

* ``is_shareable(obj)``
      Return True if the object's type supports sharing.

* ``as_shareable(obj, convert=None, *, fallback=None)``
      Convert the given object to raw cross-interpreter data.  Return an
      object that wraps that data.  This gives users a chance to convert
      the object before passing it to another interpreter.

      Returns a ``CrossInterpreterObjectData`` object that wraps the raw
      shareable data for the object.  This relies on the same protocol
      as :meth:`Interpreter.prepare_main` and :class:`Queue` and
      uses the same mechanism.  The main difference is that, by default,
      this does not use any fallback other than :meth:`object.__xidata__`.

      If the given object cannot be converted to with sharable data then,
      by default, :func:`as_shareable` raises ``NotShareableError``.
      This can be avoided by providing a "convert" function
      or a fallback value.

      "fallback" indicates what to do if the object (or the converted
      object when "convert" is provided) is not sharing-compatible.
      If ``True`` (or ``None``) then it only falls back to the type's
      ``__xidata__()`` method, if available, as an implicit convert
      func.  It may also be "full", which means it will do what
      :meth:`Interpreter.prepare_main` and :class:`Queue`
      do by default: try ``__xidata__()``, as a function, and then
      serialize with pickle.

      If "obj" is a :class:`CrossInterpreterObjectData` then it is
      returned as-is.

Attributes and methods:

      If so, ``as_object()`` and ``as_converted_object()`` will

* ``as_object()``
      Returns an object corresponding to the data, applying any
      unwrapper as necessary.  This essentially restores the
      original object or a copy of it.

* ``as_converted_object()``
      Returns (obj, restore) if the original object was "wrapped".
      "obj" is the actual object that was converted to cross-interpreter
      data, corresponding to the result of converting the original object.
      "restore" is the function to get the object corresponding to the
      original, as described for :func:`as_shareable()`.

      Returns (obj, None) if the original object was not converted,
      the same as the ``as_object()`` method.

Exception
---------

``concurrent.interpreters.NotShareableError``
      Indicates that an object was not shareable.


Specification: C-API
====================

At the lower level (C layer), the fundamental problem to solve
is sharing data safely between two interpreters.  This refers
to both thread-safety (mutation) and managing lifecycles
(deallocation).

The proposed C-API falls into two catagories:

1. users - passing objects/data between interpreters safely
2. types - supporting cross-interpreter instances

These categories effectively operate on the same data type.
However, they use a different API prefix to reflect the distinction.

Using Cross-Interpreter Data
----------------------------

The following API facilitates passing object-derived data between
interpreters safely.  It is inspired by the :pep:`3118` buffer API.

Usage will typically follow this pattern::

   /* interpreter A */

   PyCrossInterpreterData *xid = PyObject_GetCrossInterpreterData(obj);
   if (xid == NULL) {
       return -1;
   }

   /* interpreter B */

   PyObject *obj = PyCrossInterpreterData_NewObject(xid);
   PyCrossInterpreterData_Release(xid);
   if (obj == NULL) {
       return -1;
   }

The new API:

::

   typedef struct xid PyCrossInterpreterData

The opaque type that encapsulates the information needed to safely
pass/share data between interpreters.

::

   int PyObject_CheckCrossInterpreterData(PyObject *obj)

Return true if the object's type supports "sharing".

::

   PyCrossInterpreterData * PyObject_GetCrossInterpreterData(PyObject *obj);

Return the cross-interpreter data corresponding to the object.

::

   PyObject * PyCrossInterpreterData_NewObject(PyCrossInterpreterData *xid)

Return a new object corresponding to the given data.

::

   int PyCrossInterpreterData_Release(PyCrossInterpreterData *xid)

Release the associated object, if any, and free the raw data,
if necessary.  Both tasks are performed in the original interpreter.
If that is the current interpreter then it happens immediately.
Otherwise it happens "soon" in any one of that interpreter's threads
where the eval loop is running.

Regardiess, the given "xid" is always deallocated after the object
and raw data have been released.

Defining a Cross-Interpreter Type
---------------------------------

For cross-interpreter data to be useful, there must be a way for types
to define how their instances are converted to cross-interpreter data
and back.

That involves:

1. a function to convert an instance of the type to raw data
2. a function to convert raw data back into an object

The new API:

::

   typedef struct xid Py_xid_t

The opaque type that encapsulates the information needed to safely
pass/share data between interpreters.

::

   typedef int (*xidfunc)(PyThreadState *, PyObject *, Py_xid_t *)

   /* for builtin static types and internal data */
   typedef struct {
       ...
       xidfunc tp_xid;
       ...
   } PyTypeObject

   /* for heap types */
   #define Py_tp_xid 82

For a type to define that its instances are shareable, it must have its
``tp_xid`` slot set.  This function takes the current thread state, an
instance of the type, and a cross-interpreter data object.  The function
must initialize the cross-interpreter data using the instance.  This
includes the raw data and the function to convert it back to an object.

::

   typedef PyObject *(*xid_newobjectfunc)(Py_xid_t *xid, void *data)
   typedef void (*xid_freefunc)(void *);

   void PyXID_InitWithData(Py_xid_t *xid, void *data,
                           xid_newobjectfunc new_object,
                           xid_freefunc free)

   void PyXID_InitWithObject(Py_xid_t *xid, void *data, PyObject *obj,
                             xid_newobjectfunc new_object,
                             xid_freefunc free)

   void * PyXID_InitWithSize(Py_xid_t *xid, const size_t size,
                             xid_newobjectfunc new_object);

In the ``tp_xid`` function, the type uses one of these functions
to initialize the cross-interpreter data.

``PyXID_InitWithData()`` is used when the raw data already exists,
but isn't associated with the object (or with the object's lifetime).
This can be useful in a number of situations, such as when the object
maps to an entry in a static lookup table or is a singleton.
No memory is allocated and the caller is responsible for cleaning up
(if needed).

``PyXID_InitWithObject()`` is used when the raw data comes from
(or is tied to the lifetime of) an object, like the underlying data
of a ``bytes`` object.  No memory is allocated, but it is expected
that the raw data will be deallocated when the object is deallocated.

``PyXID_InitWithSize()`` is used when the raw data will be filled in
dynamically afterward.  This implies it is completely independent
of the object's lifetime.

In each case, the "data" arg may be ``NULL``, but the "newobject"
function is required.  This function is called by
``PyCrossInterpreterData_NewObject()``.

::

   int64_t PyXID_GetInterpID(PyCrossInterpreterData *xid)

The "newobject" function set by the type may need additional data
stored in the cross-interpreter data.  These helper functions provide
that information.
